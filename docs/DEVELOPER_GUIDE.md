# SL Flights. Руководство разработчика

Откройте [BookingTests.java](../src/test/java/ru/qa/flights/tests/BookingTests.java), запустите `BOOK-01` из IntelliJ IDEA и сравните шаги в коде с отчётом Allure. Команды запуска и полный список сценариев собраны в [README](../README.md).

## Как устроен прогон

1. Gradle читает [config/test.properties](../config/test.properties), выбирает браузер и передаёт параметры в JVM тестов. Команда с `-P` переопределяет настройку на один запуск. `prepare` компилирует тесты и распаковывает Allure CLI. Gradle Wrapper задаёт версию Gradle.
2. JUnit находит тесты. Перед каждым сценарием `BrowserTest` создаёт отдельный сеанс WebDriver. Перед завершением упавшего сценария он пытается приложить скриншот. После теста `driver.quit()` закрывает браузер. `SM-01` идёт первым при запуске набора, остальные тесты сами создают нужное им состояние. [BrowserTest.java](../src/test/java/ru/qa/flights/support/BrowserTest.java)
3. `BrowserFactory` подбирает драйвер Chrome или Firefox через Selenium Manager один раз для браузера в тестовой JVM. Следующие сценарии повторно используют найденные пути и создают новые сеансы. Для Safari используется драйвер macOS или настроенный узел Selenium Grid. [BrowserFactory.java](../src/test/java/ru/qa/flights/support/BrowserFactory.java)
4. Allure сохраняет шаги, статусы и вложения отдельно для каждой задачи и браузера. `allureReport` выполняется после всех выбранных тестовых задач в той же команде. Configuration Cache хранит граф задач Gradle, а UI-сценарии выполняются при каждом прогоне. [build.gradle](../build.gradle)

## Page Object для приложения с одним URL

SL Flights меняет видимый блок при переходе между входом, поиском, таблицей и бронированием. Обычно адрес остаётся тем же. Поэтому сценарии ждут нужный элемент и проверяют состояние экрана. [Требования SR-05-01 и SR-05-02](https://slqamsk.github.io/cases/slflights/)

| Класс | Ответственность |
| --- | --- |
| `LoginPage` | Открыть форму, заполнить и отправить её, прочитать ошибку |
| `SearchPage` | Выбрать оба города и дату, начать поиск, выйти из сессии |
| `ResultsPage` | Прочитать строки и счётчик, изменить сортировку, выбрать рейс |
| `BookingPage` | Прочитать детали рейса, изменить данные пассажира, отправить форму и прочитать подтверждение |
| `Page` | Общие явные ожидания и ввод в поля |

Классы страниц хранят локаторы и возвращают то, что прочитали из интерфейса. Проверки JUnit находятся в тестах. Например, `ResultsPage.flights()` преобразует текст ячеек в объекты `Flight`, а `ResultsTests` сверяет их порядок со своим ожидаемым списком. Если изменился HTML, начните с локатора в Page Object. Если изменилось подтверждённое требование, обновите ожидаемый результат сценария. [Страницы проекта](../src/test/java/ru/qa/flights/pages), [Page Object Model в Selenium](https://www.selenium.dev/documentation/test_practices/encouraged/page_object_models/)

## Разбор BOOK-01

1. `FlightTest.signIn()` открывает форму, отправляет данные учебной учётной записи и ждёт появления поиска. После нажатия «Войти» сайт показывает промежуточное сообщение, поэтому ожидание привязано к форме поиска.
2. `nextScheduledSearch(...)` рассчитывает ближайший **будущий** понедельник по календарю браузера. Тест выбирает Москву и Лондон. `SearchPage` записывает ISO-дату в DOM-поле `type=date` и отправляет события ввода и изменения. Так даты одинаково вводятся в браузерах с разными нативными масками. Поиск запускается обычным нажатием «Найти».
3. `ResultsPage.book(...)` находит строку по маршруту, дате, времени и цене из набора данных. Строка может перемещаться при сортировке. Поиск по данным рейса сохраняет выбор после перестановки строк.
4. Тест сверяет детали рейса и четыре предзаполненных поля. Затем вводит другие учебные ФИО, паспорт, email и телефон и отправляет форму.
5. Тест проверяет сообщение «Регистрация успешно завершена!» и читает JavaScript-диалог через `alertIsPresent()`. Он закрывает диалог и сравнивает его текст с выбранным рейсом и введёнными данными. При сравнении учитывается различное отображение разделителя тысяч в браузерах.

Сравните с `BOOK-07`: он прерывает бронирование кнопкой возврата и повторно открывает тот же рейс, чтобы убедиться, что подставлены исходные данные профиля. [BookingTests.java](../src/test/java/ru/qa/flights/tests/BookingTests.java)

## Как менять тесты

- **Данные и ожидаемые тексты.** `data/test-data.json` хранит публичные учебные учётные записи, расписание и ожидаемые сообщения. `TestData` читает файл через Jackson и сообщает об отсутствующих полях. Для эксперимента скопируйте JSON в `data/experiment.local.json` и запустите с `-PdataFile=data/experiment.local.json`. Файлы `data/*.local.json` игнорируются Git. [Данные](../data/test-data.json), [TestData.java](../src/test/java/ru/qa/flights/data/TestData.java)
- **Новое значение при тех же шагах.** Возьмите `BOOK-02` как пример. В `invalidPassengerFields()` каждый объект задаёт ID, название, поле, ввод и ожидаемую ошибку. JUnit выполняет каждый вариант в отдельном браузерном сеансе.
- **Новая последовательность действий.** Для нового перехода добавьте метод `@Test` с `@DisplayName`, опишите шаги через `Allure.step(...)` и переиспользуйте методы Page Object. Запишите ID требования в таблицу README.

## Как разбирать упавшую проверку

1. В Allure найдите ID, браузер и первый упавший шаг. Сравните ожидаемое значение с фактическим и откройте вложенный скриншот.
2. Сохраните HTML до повторного запуска. Для одиночной проверки можно использовать функцию запуска метода в IDEA или фильтр Gradle.

   ```bash
   ./run.sh firefoxTest --tests '*ResultsTests.sortingKeepsNoFlightsNotice'
   ```

3. При воспроизведении зафиксируйте версию стенда, браузер, шаги и расхождение с BR/SR. Ожидаемый результат берите из требования. Если ожидание тайм-аутится, сначала проверьте фактический экран и локатор, чтобы отличить ошибку автоматизации от дефекта приложения.
